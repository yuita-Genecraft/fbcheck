# fbcheck

AIに作ってもらったアプリを公開する前に、**実際に漏れた事例と同じ穴が空いていないか**を、自分の目で確認するツールです。

```bash
node fbcheck.mjs ./your-project
```

インストール不要。依存パッケージなし。**ネットワークに出ません**（あなたのPCの中のファイルしか読みません。他人のアプリを調べることはできません）。

---

## 何が違うのか

このツールは「安全です」とは言いません。**あなたのファイルの実物を引用します。**

```
2. ログインさえすれば他人のデータも読めます（firestore.rules）

   根拠（あなたのファイルの実物）:
     firestore.rules:8  allow read, write: if request.auth != null;

   なぜ危ないか:
  `request.auth != null` は「ログイン済みなら誰でも許可」です。
   自分のデータだけ、という条件が入っていません。
```

判定の結果ではなく、判定の材料を出します。`request.auth != null` に「自分のだけ」という条件が入っていないことは、コードが読めなくても見れば分かります。**このツールを信用する必要がありません。**

---

## 「直さなくていいもの」も言います

セキュリティツールは普通、危険なものしか教えてくれません。でも初心者が時間を溶かすのは、**直さなくていいものを直そうとしている時**です。

fbcheck はそこも出します。

```
■ 直さなくていいもの（よくある誤解）

1. Firebase の apiKey がフロントに出ているのは、正常です

   これは秘密の鍵ではなく、どのプロジェクト宛かを示す識別子です。
   ここを隠そうとして時間を使う人が多いのですが、
   守っているのは apiKey ではなく「セキュリティルール」の方です。
```

---

## 見ているもの（4か所）

実際の漏洩事例で最も多かった場所に絞っています。

| | 見るもの |
|---|---|
| ① | セキュリティルールの `if true`（誰でも読み書きできる状態） |
| ② | `request.auth != null` だけの許可（ログインすれば他人のデータも読める） |
| ③ | 配布ファイル（dist / build / public）に混ざった秘密鍵 |
| ④ | `.env` の扱いと、`NEXT_PUBLIC_` 系の取り違え |

あわせて、テストモードのルールが残っていないか、Realtime Database が全公開になっていないかも見ます。

Firebase を使っていないプロジェクトでは、ルールの項目は判定せず、鍵まわりだけ確認します。

---

## 使い方

```bash
# Node.js 18 以上
node fbcheck.mjs              # カレントディレクトリ
node fbcheck.mjs ./my-app     # パス指定
```

終了コードは、公開前に直すものがあれば `1`、なければ `0`。CIに入れることもできます。

---

## 限界（正直に）

- **見ているのは上の4か所だけです。** ここが通っても、アプリ全体が安全という意味にはなりません
- ルールファイルの静的な読み取りなので、**Firebaseコンソール側で直接編集したルールは見えません**。その場合はコンソールのルールタブの中身を確認してください
- 秘密鍵の検出は既知のパターン照合です。見落としがあります
- 逆に、**ここが赤い場合は実際に漏れた事例と同じ形になっています**

---

## 作った理由

AIで開発している人が「AIの言っていることが正しいか、自分では判断できない」と詰まっているのを見たのがきっかけです。

セキュリティルールは、AIが最も間違えやすく、かつ**間違えていることに本人が気づけない**場所でした。だから「危ないから直せ」ではなく、**何がどう書いてあるか**を出す形にしています。
